El developer toca 6 puertas; sooft es el núcleo que rige y reparte el trabajo.
Regla de oro: el agente no escribe una sola línea de código hasta que el PLAN está aprobado explícitamente (phase ∈ {PLAN_APPROVED, FIX_PLAN_APPROVED, REMEDIATION_PLAN_APPROVED, IMPLEMENTING}). Antes de eso solo produce artefactos del proceso (discovery, PRD, SPEC, PLAN).

Lo que invoca el developer

Las 6 skills con slash command

Son las únicas entradas que el developer dispara (con / en VS Code o en lenguaje natural en el CLI). Cada router conduce una rama de la máquina de estados y delega en skills internas.

/sooft

Constitución + init

Punto único de arranque. Muestra el banner, instala los hooks, crea .sooft/, detecta stack e integraciones y configura el MCP del issue tracker. Define todas las reglas que rigen al resto.

always-on fuente de verdad

Assets: init.md, banner.txt, sooft.json, copilot-instructions.md, prompts/, templates/, drivers/, reviews/, policies/, archetypes/ + 9 skills internas en internal/

/sooft-development

Features · migraciones · refactors

Orquesta la rama de features. Conduce discovery → PRD → SPEC (si es complejo) → PLAN → implementación → revisión → PR. No escribe código hasta PLAN_APPROVED.

  • assets/prd.md
  • assets/technical-spec.md
  • assets/implementation-plan.md
/sooft-bugs

Bugs · regresiones

Orquesta la rama de bugs. Documenta → causa raíz → reproducción (test que falla primero) → fix plan → fix → revisión. El test de reproducción no se reescribe después.

  • assets/bug-analysis.md
  • assets/bug-reproduction.md
  • assets/fix-plan.md
/sooft-security-remediation

Vulnerabilidades · hallazgos

Orquesta la rama de seguridad. Hallazgos → scope → plan de remediación → fixes → re-scan. Siempre corre en Opus; no aplica TDD (re-scan + regresión).

Opus
  • assets/security-findings.md
  • assets/security-scope.md
  • assets/remediation-plan.md
/sooft-status

Estado del pipeline

Read-only. Muestra la fase actual, el type, los artefactos generados y el próximo paso. No modifica nada: solo lee .sooft/state.json y la evidencia.

read-onlysin assets
/sooft-incident-response

Incidente en producción

Para un INC activo que requiere hotfix urgente. Igual que bugs pero con la urgencia de producción: puede habilitar un fix directo con los controles mínimos.

hotfixsin assets
El motor que el developer no ve

Skills internas

Son skills internas, no invocables por el developer: viven en skills/sooft/internal/*.md y no tienen slash command propio. Los routers las cargan leyendo el archivo en el momento correcto del flujo. Viajan con sooft, que se carga siempre.

RecursoSe carga cuando…
internal/sooft-discovery.mdarranca cualquier flujo — discovery obligatorio antes de tocar nada
internal/sooft-implement-task.mdhay que ejecutar una tarea aprobada del plan
internal/sooft-validation.mdvalidación pre-PR (/review): linter + calidad + SAST
internal/sooft-code-review-gate.mdgate de aprobación humana del código [IA-generated]
internal/sooft-evidence.mdhay que registrar evidencia en .sooft/evidence.md
internal/sooft-adr.mdsurge una decisión de arquitectura significativa
internal/sooft-test-strategy.mdse define qué y cómo testear durante el planning
internal/sooft-release.mdel PR fue aprobado y hay que preparar el deploy
internal/sooft-maintenance.mdel trabajo es tipo chore / mantenimiento

El control humano

Los 4 gates de aprobación

En cada gate el agente emite la frase canónica y se detiene: no avanza hasta el OK explícito del developer. No se infiere un “sí”, no se saltea un gate.

El corazón determinista

Máquina de estados

El campo type de .sooft/state.json elige la rama. Las tres convergen en un tronco común (validación → revisión → PR). Un phase no enumerado o una transición no listada ⇒ el agente se detiene.

    RL --> FEAT{{"type?"}}

    FEAT -->|feat| F1["ANALYZED → PRD → SPEC* → PLAN_APPROVED"]
    FEAT -->|bug| B1["BUG_DOCUMENTED → ANALYZED → REPRODUCED → FIX_PLAN_APPROVED"]
    FEAT -->|security| S1["FINDINGS → SCOPE_CONFIRMED → REMEDIATION_PLAN_APPROVED"]

    F1 --> IMP[IMPLEMENTING]
    B1 --> IMP
    S1 --> IMP

    IMP --> VAL[VALIDATING]
    VAL -->|"SAST crítico/alto"| SF[SECURITY_FINDINGS]
    SF --> VAL
    VAL --> CR[CODE_REVIEW_PENDING]
    CR --> RD[REVIEW_DONE]
    RD --> PRO[PR_OPEN]
    PRO --> DONE([DONE])

Switcheo por complejidad

Modelos

SOOFT corre en Sonnet como base y ajusta el modelo según la complejidad del pedido. El developer no decide esto — lo decide el agente, con sesgo conservador: ante cualquier señal de seguridad o arquitectura, escala.

Haiku

Tareas SIMPLE

Typo, renombrar, formatear, comentarios, status, consultas de "qué es / cómo funciona". Trabajo mecánico que no justifica el modelo grande.

Sonnet

Tareas STANDARD · base

Feature común, bug común, tests. El modelo por defecto con el que corre toda la sesión.

Opus

Tareas COMPLEX

Arquitectura, seguridad, auth, migración, datos sensibles, concurrencia, performance crítico. Al escalar, el agente lo dice explícitamente y por qué.

Regla de oro: nunca se degrada algo crítico a Haiku. Ante cualquier señal de seguridad o arquitectura, el agente escala a Opus — no al revés.
No negociables

Los 9 principios fundacionales

Cada skill, regla y template se apoya en esto. Ante la duda, se vuelve acá.

Gate-drivenNo se avanza en un punto crítico sin aprobación explícita.
PRD colaborativoEl scope se afina con ida y vuelta antes de cerrarlo.
Spec cuando importaSPEC técnica solo para cambios complejos o riesgosos.
Artefactos por tipoRastro en docs/feats, docs/bugs o docs/security.
Worktree-firstSe trabaja en .worktrees/{tipo}-{slug}, nunca sobre la rama compartida.
Nombres tipo Gitfeat, fix, hot-fix, chore, security.
Tool-agnosticLas herramientas se detectan o configuran por proyecto; no se asumen.
Security-by-defaultTodo cambio pasa por validación, tests y controles de seguridad.
AuditabilidadCada trabajo deja decisión, plan, evidencia e historial.
