¿Qué es SOOFT?

Una metodología, no un autocompletado

SOOFT es el marco que convierte a un asistente de IA en un compañero de equipo disciplinado: piensa profundo, pero no toca el código hasta que vos diste el OK.

🚦

Gate-driven

En cada punto crítico el agente se detiene y espera tu aprobación explícita. No se infiere un "sí".

🔍

Discovery primero

Antes de leer una línea, una ronda corta de preguntas con opciones desambigua el requerimiento.

🌿

Worktree-first

Cada trabajo vive aislado en su propio worktree. Nunca toca la rama compartida por accidente.

🛡️

Security-by-default

Sin secretos en código, sin PII en logs. Linter, calidad y SAST antes de cualquier PR.

🧪

Test-first

Para lógica nueva, el test va antes de la implementación. Los bugs arrancan reproduciéndose.

📜

Auditabilidad

Cada trabajo deja decisión, plan, evidencia e historial rastreables. Listo para auditoría.

🧭

Enrutamiento automático

El orquestador clasifica riesgo/complejidad y decide qué subagente y qué modelo resuelve cada etapa — vos nunca elegís el modelo.

🧩

Rigor variable (DIRECT/LEAN/FULL)

No todo feature necesita PRD. Un cambio trivial pasa directo; uno acotado salta el PRD; uno complejo hace el pipeline completo.

🔌

Tool-agnostic

Funciona igual en Claude Code, GitHub Copilot, Cursor, Kiro, Windsurf o cualquier herramienta que lea AGENTS.md — no depende de un solo proveedor.

¿Cómo se usa?

Del requerimiento al PR, con control en cada paso

Un flujo donde vos mantenés el control en cada compuerta.

Discovery

El agente pregunta lo justo (con opciones para elegir) y registra el contexto antes de tocar nada.

→

Rigor

Clasifica DIRECT / LEAN / FULL según riesgo real (no palabras clave) y te pide confirmarlo.

→

PRD / PLAN

Según el rigor confirmado: PRD completo, o directo al PLAN. Tareas numeradas, test-first para lógica nueva.

→

Implementación

Recién acá escribe código, tarea por tarea, marcado como [IA-generated] para tu revisión.

→

Review + PR

Validación (tests, SAST), autoevaluación y tu aprobación final antes de abrir el PR.

Regla de oro: el agente no escribe una sola línea de código hasta que el plan de la rama activa está aprobado — salvo un cambio clasificado DIRECT (trivial, reversible, sin lógica), donde el gate es presentar el diff para tu revisión antes del PR. Ese es el único caso documentado que llega a implementación sin un PLAN.md de por medio.
Instalación

Dos formas de usar SOOFT, de punta a punta

Sin instalar nada (para probarlo hoy) o instalado con el CLI (para el uso diario del equipo).

1

Instalá el CLI

Paquete @sooft/cli, cero dependencias de runtime, Node ≥ 18.

PowerShell — instalar @sooft/cli
─□✕
PS> npm i -g @sooft/cli # o sin instalar global: npx @sooft/cli <comando>
2

Apuntá a los estándares

Una sola vez: repo owner/repo, URL git, o path local.

PowerShell — configurar la fuente
─□✕
PS> sooft agent source sooft-tech/sooft-ai-standards ✓ Standards source set → sooft-tech/sooft-ai-standards
3

Instalá en tu proyecto

Detecta las herramientas de IA presentes y coloca skills, subagentes ocultos y AGENTS.md en cada una.

PowerShell — instalar el agente
─□✕
PS> sooft agent install ✓ Installed Sooft AI Rails → claude, copilot 8 skill(s), 10 subagent(s)
4

Administralo cuando haga falta

Todo lo que instaló queda en un manifest — se actualiza o se saca exacto.

PowerShell — mantenimiento
─□✕
PS> sooft list # qué está instalado PS> sooft check # detecta drift PS> sooft agent update # reinstala, reemplaza lo anterior PS> sooft agent remove # saca exactamente lo que instaló

Funciona para cualquier herramienta de IA, no solo las que ya tienen soporte nativo: Claude Code, GitHub Copilot, Cursor, Kiro, Windsurf y un target genérico .agents/ para el resto — todas reciben skills + subagentes ocultos + AGENTS.md siempre-activo.

1

Instalá las skills

Una sola vez por proyecto, para todos los agentes.

PowerShell — npx skills add
─□✕
PS> npx skills add sooft-tech/sooft-ai-standards -a '*'
2

Inicializá el proyecto

Una sola vez por repo. Detecta stack, integraciones y crea .sooft/.

PowerShell — init
─□✕
PS> /sooft [ticket]

Después, /sooft-development, /sooft-bugs, /sooft-security-remediation o /sooft-migrations según el tipo de trabajo — o describilo en lenguaje natural y el agente rutea solo.

✓

Nada que instalar

Dale al agente este repo como contexto y decile: "seguí sooft-ai-standards, necesito X". Funciona toda la metodología (fases, gates, templates); lo único que falta es el bloqueo físico de los hooks.

Es la forma más rápida de probar SOOFT antes de instalarlo para todo el equipo.

Enrutamiento automático

Modelos y subagentes

SOOFT corre en Sonnet como base y clasifica cada pedido por señales estructurales — no palabras clave — para decidir modelo y ruta de subagentes. El developer no elige esto por defecto.

SIMPLE → Haiku

Typo, renombrar, formatear, comentarios, status. Trabajo mecánico que no justifica el modelo grande.

STANDARD → Sonnet

Feature común, bug común, tests. El modelo por defecto de toda la sesión.

COMPLEX → Opus

Arquitectura, refactor grande, migración, concurrencia, causa raíz desconocida.

CRITICAL → Opus + reviewer

Auth, PII, pagos, migraciones de datos, config de producción. sooft-security-reviewer obligatorio en la ruta, sin excepción.

Subagentes ocultos. Los 10 subagentes (sooft-discovery, sooft-prd-writer, sooft-security-reviewer…) se declaran user-invocable: false: no aparecen en ningún selector manual. El developer solo ve los 8 routers; el orquestador decide, programáticamente, cuál subagente y qué modelo resuelve cada etapa.
Gobierno de fallback. Una ruta CRITICAL nunca degrada a un modelo rápido si el principal no está disponible — bloquea y notifica. sooft-code-reviewer nunca corre con el mismo modelo que implementó el cambio. Ninguna tarea cambia de modelo dentro de una misma respuesta ya iniciada.
